# Publishing scripts

These Python scripts prepare and validate the `wq-wasm` npm package and cut a
shared Cargo and npm workspace release. They resolve repository paths from
their own location instead of the current working directory. The examples below
assume the current directory is the workspace root.

## Requirements

- Python 3.11 or newer
- Cargo 1.90 or newer
- Node.js 24
- npm 11.18.0
- wasm-pack 0.15.0

The scripts use only the Python standard library. The release command invokes
Cargo, Git, npm, and wasm-pack through the npm package scripts.

## Commands

### Prepare the npm package

`prepare_package.py` copies the npm ignore rules into the output generated by
wasm-pack. `npm run build` runs it automatically after the WebAssembly build:

```sh
cd wq-wasm
npm run build
```

Run it directly only after `wq-wasm/pkg` exists:

```sh
python3 publish-scripts/prepare_package.py
```

### Validate npm package metadata

`check_package.py` checks the source package manifest, generated package
manifest, Cargo metadata, repository URL, and optional release tag. It prints
the npm dist-tag and writes `npm_tag` to `GITHUB_OUTPUT` when that variable is
set.

After building the package, run:

```sh
python3 publish-scripts/check_package.py
```

Validate a specific release tag in the same way CI does:

```sh
RELEASE_TAG=v0.9.0-preview2 python3 publish-scripts/check_package.py
```

### Test the publishing tools

Run the standard-library unit tests from the workspace root:

```sh
python3 -m unittest discover \
  -s publish-scripts \
  -t publish-scripts \
  -p 'test_*.py'
```

### Cut a workspace release

`release.py` requires a clean worktree and a checked-out branch. It performs
the following operations:

1. Resolves publishing remotes and verifies exactly one points to
   `github.com/wqpl/wq`.
2. Updates the shared Cargo version, versioned workspace path dependencies,
   `Cargo.lock`, and `wq-wasm/package.json`.
3. Runs the Python tests, Rust formatting and Clippy, the `wq-wasm` Rust tests,
   a Cargo workspace publish dry run, and the npm build, validation, tests, and
   package inspection.
4. Verifies that only the three expected version files changed.
5. Creates a release commit and annotated `vVERSION` tag.
6. Offers to push each mirror first and GitHub last. Every remote receives the
   branch and tag in one atomic push. The GitHub tag triggers package
   publishing.

The command never runs `npm publish` locally.

Configure the default publishing remotes once:

```sh
git config remotes.publish "github codeberg"
```

Without that setting, the command uses `github` when that remote exists and
otherwise uses `origin`.

Show all options:

```sh
python3 publish-scripts/release.py --help
```

## Example workflows

### Publish the next preview

With a current version such as `0.9.0-preview1`, omit the version to increment
the trailing number:

```sh
git status --short
python3 publish-scripts/release.py
```

Review the displayed remote order before answering the push prompt. A `yes`
pushes mirrors first, then GitHub.

### Publish an explicit preview or stable release

Pass a SemVer when the version line changes or a preview becomes stable:

```sh
python3 publish-scripts/release.py 0.10.0-preview1
python3 publish-scripts/release.py 0.10.0
```

A leading `v` is accepted. The target must have higher SemVer precedence than
the current workspace version.

### Create the release locally without pushing

Use `--no-push` to run all checks and create the local commit and tag without a
prompt:

```sh
python3 publish-scripts/release.py --no-push
```

The command prints the exact atomic push commands for later use. This option
still creates the release commit and tag.

### Override publishing remotes for one release

Repeat `--remote` to replace the Git configuration for one invocation:

```sh
python3 publish-scripts/release.py 0.10.0 \
  --remote codeberg \
  --remote github
```

The GitHub remote is always reordered last, regardless of argument order.

### Exercise the GitHub Actions workflow without publishing

Manually dispatch `publish-wq-wasm.yml`. A manual dispatch builds, validates,
tests, and inspects the npm package but skips `npm publish`. Pushing a matching
`vVERSION` tag runs the same checks and publishes with npm trusted publishing.

## Failure and recovery behavior

Before Git staging begins, a failed release check restores `Cargo.toml`,
`Cargo.lock`, and `wq-wasm/package.json` to their original contents. Other files
are never rewritten by the recovery path.

After Git staging begins, the script leaves the index, release commit, and tag
untouched so it does not discard Git state. Inspect them before retrying:

```sh
git status
git show --stat --oneline HEAD
git tag --points-at HEAD
```

When a mirror push succeeds and a later push fails, rerun only the displayed
atomic push command for each remaining remote. GitHub stays last because its tag
push starts the crates.io and npm workflows.
